Updated revoked-device query to match absent/null fields safely, made expected stale-pairing errors log as warnings rather than stack traces, and made popup status report disconnected with a re-pair action.

The Dashboard exposes recent, owner-scoped past runs, which open Recruiter Discovery at that run.

- The current Chrome extension records job-application tasks; it does not itself write recruiter posts into `RecruiterLead`. This page intentionally lists the existing shared `RecruiterLead` records written by Recruiter Discovery, rather than creating a separate extension dataset. Extension-originated leads will appear only if an existing source writes them to this model.

### Duplicate saves, search latency, and visible waiting state (2026-10-11)

- Root cause for extracted emails missing from the listing: a prior deployment can retain the old unique `{ firebaseUid, primaryEmail }` MongoDB index even though the current schema declares it non-unique. That index blocks distinct posts sharing an email and empty-email posts. On startup, RecruiterService now removes only that exact legacy unique index and ensures the current schema indexes. The unique `{ firebaseUid, sourceKey }` index remains the intended post deduplication mechanism.
- Duplicate-key errors are now called duplicates only if a record with the matching source key is found. Any other duplicate-key conflict is logged as a real save failure instead of reporting a post as already saved without persistence.
- Reduced Playwright card discovery from many serial locator/ancestor calls to one in-page candidate scan. Expanded-post buttons are found in-page and capped to a small number of explicit “see/show more” matches. Already-processed cards are skipped before expansion, so visible results aren't repeatedly rescanned/expanded.
- Live activity now emits real wait messages while LinkedIn loads initial/additional cards and displays an animated elapsed waiting indicator after activity has been quiet for three seconds.
- Verification: focused recruiter tests pass (18 tests); backend, frontend, and automation builds pass. Live MongoDB index migration and end-to-end LinkedIn speed/DOM behavior remain unverified without the deployed database and signed-in browser.

### LinkedIn post-card retry fallback (2026-10-11)

- Post-card discovery scans the rendered DOM for bounded, visible feed-post containers and the smallest usable container around a “Feed post” label; it no longer requires Like/Comment/Repost buttons to consider a visible post.
- If cards are unavailable, the updated runner retries once by reloading the same Posts search and scanning again. If still unreadable, it logs a warning and `post.skipped`, then exits normally without claiming any post was processed.
- Compatibility handling recognizes the legacy runner’s exact “no accessible post cards appeared within 20 seconds” error from the user's log and completes that run as a warning/skip rather than a failure. This is needed because the submitted log is from the older 20-second runner path; restarting `npm run linkedin:local` loads the 10-second initial scan + one retry and prevents that old error from being reported in the first place.
- Validation: local automation build, backend build, and focused recruiter service tests pass (12 tests), including compatibility handling for the exact legacy error. Live LinkedIn behavior remains a user-browser verification.
